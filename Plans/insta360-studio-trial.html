Scope, assumptions & guardrails

  • GO 3S records H.264 MP4, up to 4K30; FreeFrame is 3840×2880. Test FlowState, horizon lock, FOV, aspect ratio, audio and export—not dual-lens stitching or 8K.
  • Dedicated rootless Ubuntu 24.04 Distrobox, persistent separate Wine prefix, existing host NVIDIA driver, Xwayland first. Trial uses a custom home; final toolbox uses normal shared host home for standard desktop export integration.
  • BoxKit image/CI and dotfiles source changes authorized by the user's adoption request. No host package layering, driver changes, Flatpak installation, camera firmware updates, importer changes, commits, pushes or global chezmoi apply.
  • No Wine as root. Install Linux dependencies using container sudo only.
  • Use small byte-identical copies of originals; never remux or transcode inputs before Studio. Keep exports separate. Do not execute the importer or delete camera files.
  • Distrobox can access personal files despite a custom home. Trusted installers only; no broad permission changes or security disabling to fix graphics.
  • At most two clean Studio/Wine version combinations initially. Diagnose logs rather than piling on DLL overrides.
  • Potential user gates: official download authentication, installer agreement, selecting representative media, visual judgment of stabilization and output quality.

Acceptance checklist

  1. Copy one short normal video and one short FreeFrame video into trial inputs; verify SHA-256 against originals. Ask user to identify modes if metadata is inconclusive.
  2. Open and scrub both clips. Confirm image, audio, expected duration and camera metadata recognition.
  3. On FreeFrame, apply FlowState, horizon lock and supported FOV options; test landscape and portrait framing.
  4. Export H.264 MP4 at 1080p, then target 4K. Check output using ffprobe/decoder and a Linux player. Compare stabilization visually; no black frames, corrupt frames or audio drift.
  5. Save edits, close/reopen Studio three times, then stop/start the container. Edits and export functionality must survive.
  6. Test one longer representative clip; record duration, export wall time, peak VRAM, GPU encoder/decoder activity and disk use.
  7. Record user verdict: acceptable preview responsiveness and export quality. Software encoding may pass functional proof; it does not establish NVIDIA acceleration.

Original gate required verified GO 3S FreeFrame export before adoption. The user explicitly requested packaging after reporting Studio works; that changes scope, not the evidence. A working UI or nvidia-smi still does not establish export correctness or hardware encoding.

UI scaling — working, user confirmed

Original Wine DPI=96 made controls tiny on 2560×1600 at niri scale 1.5. LogPixels=144 enlarged controls but left half the client area black; 192 DPI reproduced that layout issue. Restoring 96 DPI and trying QT_SCALE_FACTOR=1.5 did not enlarge the final full-width UI. Final successful combination: HKCU\Control Panel\Desktop\LogPixels DWORD 144 plus environment QT_ENABLE_HIGHDPI_SCALING=0. This points to an interaction between Studio/Qt automatic scaling and Wine geometry; precise upstream cause is not established.

Verified whole-window rendering at 150%; user said “working better.” Screenshots: logs/studio-first-launch.png (before), logs/studio-dpi144-qt-disabled.png (working).
